# LLM KV Cache 存储基准测试标准化规范

> 版本 v1.0 · 适用于 vLLM + LMCache 推理栈，量化外部存储（远端 NVMe-oF 全闪阵列 / 本地 NVMe）对 KV Cache 卸载/回读的推理性能价值。厂商无关，已在沐曦 MetaX 上验证，可扩展至英伟达、AMD 及其他国产 GPU。完整复现代码见各厂商专页。

---

## 1. 测试目标与背景

### 1.1 要回答的问题

当 KV Cache 装不进 GPU 显存时，把它卸载到外部存储、用时再回读，相比"重新计算（recompute）"能带来多少推理性能收益？不同存储介质（远端阵列 vs 本地盘）之间又有多大差异？

### 1.2 为什么这件事容易测错

"缓存命中"可能来自三个层级，性能天差地别：

| 命中来源 | 典型 TTFT（8K 前缀） | 是否真正考验存储 |
|---|---|---|
| GPU 显存（前缀缓存 APC） | ~0.09 s | 否 |
| 主机 RAM 页缓存（page cache） | ~0.25 s | 否（**最常见假象**） |
| 物理盘（远端/本地） | ~0.44 s | 是 |

大内存主机会把刚写到盘的 KV 整份缓存在 RAM 中，若不加控制，测出来的"存储很快"其实是内存速度。**本规范的核心，就是用一套可复现、可取证的流程，强制 KV 真正从物理盘读回，并标注每一次命中的真实来源。**

### 1.3 适用栈

- 推理引擎：vLLM（含厂商移植版，如 vllm-metax）
- KV 分层库：LMCache（GPU → CPU 内存 → 磁盘多级）
- 被测存储：远端 NVMe-oF/RoCEv2 全闪阵列、本地 NVMe（单盘/RAID0）、以及"无盘重算"基线
- 加速卡：当前已覆盖沐曦 MetaX N260，方法学同样适用于英伟达 / AMD / 其他国产

## 2. 设计原则

### 2.1 单一变量

每组对照之间只允许一个变量不同（如磁盘层指向的设备），其余配置（模型、显存利用率、CPU 层大小、会话数、并发、解码长度）完全一致。每次起服后校验环境变量与容量参数，确保单一变量成立。

### 2.2 同口径四档对照

把 KV 的来源分为四档，构成从理想上界到最差下界的完整光谱：GPU 命中（上界）/ 远端存储（被测主体）/ 本地 NVMe（介质对照）/ 重算（下界）。只有同时给出上下界，中间档的数字才有意义。

### 2.3 物理读必须可证

凡声称"从存储物理盘命中"，必须同时满足：

1. KV 不在 GPU（通过"灌入会话数 ＞ 测量会话数"驱逐）；
2. KV 不在 RAM（measure 前清空页缓存）；
3. 有 `need-to-load` 计数 + `iostat` 物理读带宽双重佐证。

### 2.4 可复现 + 诚实披露

每项实验给出完整命令、参数化脚本、原始数据清单。未强制物理读（页缓存辅助）的数据必须明确标注，不得冒充物理盘性能；"装得进显存"与"超容量"两类场景分别报告。

## 4. 容量基准计算

会话数 M 的选取、物理读段位划分，都依赖一个实测量：**GPU 能装多少个会话**。

### 4.1 读取 GPU KV 容量

起服后从引擎日志读取实际可用 GPU KV 容量（token 数）：

```
GPU KV cache size: 774,704 tokens
```

> 该容量由显存利用率、模型层数/头数、KV 精度决定，与单请求长度无关。换 GPU / 显存利用率需重新实测。

### 4.2 换算可容纳会话数

```
GPU 可容纳会话数 C_GPU = GPU KV 容量(token) ÷ 单会话前缀(token)
CPU 可容纳会话数 C_CPU = LMCACHE_MAX_LOCAL_CPU_SIZE(GB) ÷ 单会话KV(GB)
```

| 档位 | GPU KV 容量 | 单会话 token | 单会话 KV | C_GPU | C_CPU(8GB) |
|---|---|---|---|---|---|
| 8K | 774,704 | 7,827 | 0.41 GB | ≈ 99 | ≈ 19 |
| 26K | 774,704 | 26,028 | 1.38 GB | ≈ 29 | ≈ 5 |

### 4.3 据此设定各档 M 与物理读段位

| 目的 | 约束 | 8K 取值 | 26K 取值 |
|---|---|---|---|
| GPU 命中（不溢出） | M ≤ C_GPU | 64 | 20 |
| 超容量（溢出到盘/重算） | M ≫ C_GPU + C_CPU | 160 | 64 |
| 物理读 populate | N_pop ≥ N_meas + C_GPU（留驱逐余量） | 160（测160） | 100（测64） |

物理读段位划分：`N_meas ≤ N_pop − C_GPU − 安全余量`。

> 26K 示例：N_pop=100，C_GPU≈29 → 显存驻留约 71–99；取 N_meas=64（读 0–63），安全余量 = 71 − 63 = 8。

## 5. 工作负载定义

### 5.1 负载模型：多会话长前缀

构造 M 个互异会话，每个带一段长前缀（模拟会话历史/系统提示/文档上下文）。

- **互异前缀**：每个会话前缀以唯一标识开头（如 `[sess-00042]`），保证不被前缀缓存跨会话去重——这是工作集能真正撑大到溢出显存的前提。
- **可控长度**：由重复因子 `reps` 控制，得两个标准档：

| 档位 | reps | 单会话前缀 token | 单会话 KV（7B/bf16） |
|---|---|---|---|
| 8K | 150 | ≈ 7,827 | ≈ 0.41 GB |
| 26K | 500 | ≈ 26,028 | ≈ 1.38 GB |

### 5.2 两阶段：populate + measure

| 阶段 | 解码长度 | 并发 | 目的 |
|---|---|---|---|
| populate | 1 token | 1（顺序） | 把 M 个会话 KV 灌入各层，建立缓存；顺序灌入保证 GPU APC 的 LRU 顺序=会话编号顺序（低编号先驱逐） |
| measure | 512 token | 16 | 受控缓存状态下测量真实推理指标，覆盖 prefill 与 decode |

### 5.3 标准负载参数

| 参数 | 含义 | 标准取值 |
|---|---|---|
| `reps` | 前缀重复因子 | 150（8K）/ 500（26K） |
| `M` | 会话数 | 见 §4.3 |
| `decode` | measure 解码 token | 512 |
| `conc` | measure 并发 | 16 |
| `temperature` | 采样温度 | 0 |

## 6. 四档对照设计

| 档位 | 标识 | KV 来源 | 工作集 vs 容量 | 磁盘层 | 角色 |
|---|---|---|---|---|---|
| ① GPU 命中 | G | GPU 显存 | 装得进 GPU | 挂着但不读 | 理想上界 |
| ② 远端存储 | D | 远端阵列物理盘 | 超 GPU+CPU | 指向远端 NVMe-oF | 被测主体 |
| ②′ 本地 NVMe | E | 本地物理盘 | 超 GPU+CPU | 指向本地盘 | 介质对照 |
| ③ 重算 | A | 无盘，重新计算 | 超 GPU+CPU | 无磁盘层 | 下界基线 |

**为什么 ① 用小 M、②③用大 M**：GPU 命中与"存储/重算"在同一会话数下互斥。M 小则四档都 GPU 命中（测不出存储）；M 大则 GPU 必溢出（测不出纯命中上界）。故 ① 用装得进显存的小 M 并验证 need-to-load=0；②/②′/③ 用统一大 M 保证溢出、三者会话数完全相同。

| 对照 | 唯一变量 | 回答的问题 |
|---|---|---|
| ② vs ③ | 有无磁盘层 | 存储相比重算的净价值 |
| ② vs ②′ | 磁盘层指向远端 or 本地 | 介质差异 |
| ② vs ① | 工作集是否溢出 | 存储离理想显存上界的差距 |

## 7. 缓存状态控制与物理读保证（核心）

要保证某次读取真正来自物理盘，必须同时把 KV 从 GPU 显存和主机 RAM 中驱逐，并取证。

### 7.1 工序 1：驱逐 GPU 显存（populate ＞ measure 段位法）

GPU 前缀缓存按 LRU 保留最近灌入的若干会话。利用这一点：

1. populate 顺序灌入 N_pop 个会话（编号 0 → N_pop−1）。
2. 灌完后 GPU 只驻留最后约 C_GPU 个会话（编号 `[N_pop−C_GPU, N_pop−1]`）。
3. measure 只读低编号段（0 → N_meas−1，且 N_meas ≤ N_pop − C_GPU），这些会话绝不在显存。

> 26K 示例：GPU 容量 ≈ 29。populate 100 → 显存仅驻留约 71–99；measure 只读 0–63 → 保证不命中 GPU。

### 7.2 工序 2：驱逐 RAM 页缓存

measure 开始前在宿主机清空 OS 页缓存：

```bash
sync; echo 3 > /proc/sys/vm/drop_caches
free -g   # 验证 buff/cache 从数十 GB 掉到个位数
```

> 该操作只清 OS 页缓存，不清 LMCache 自身 CPU 层（进程内存）；但 CPU 层小且按 LRU 保留高编号会话，measure 的低编号段早已挤到磁盘，不受影响。

### 7.3 三重取证

- **证据①（need-to-load 计数）**：measure 每个请求都 `need to load ＞ 0`（全部从盘加载）且 `computed tokens: 0`（无 GPU 命中）。
- **证据②（iostat 物理读带宽）**：measure 期间并行监控被测设备，记录物理读峰值（GB/s 量级），与 LMCache retrieve 吞吐互相印证。
- **证据③（单变量与落盘量）**：起服后校验磁盘层指向；populate 后 `du -sh` 校验落盘量与"会话数×单会话KV"吻合；重算档应 need-to-load=0、落盘 0。

### 7.4 完整时序

```
[宿主] 重启容器（清 GPU 显存到基线）
  → [容器] 起 vLLM 服务（指定磁盘层）→ 等待就绪
  → [容器] populate N_pop（前台阻塞，灌满才继续）
  → [宿主] du 校验落盘量
  → [宿主] 清页缓存（drop_caches）
  → [宿主] iostat 后台监控物理读
  → [容器] measure 低编号段 N_meas（前台阻塞）
  → [取证] need-to-load 计数 + iostat 峰值 + 结果 JSON
```

### 7.5 反面教材

同一组 26K 测量在"清缓存 vs 不清缓存"下的结果：

| 口径 | 远端存储 D | 本地 NVMe E | 结论 |
|---|---|---|---|
| 未清缓存（页缓存） | 1.371 s | 1.021 s | E 反超 D，二者都是 RAM 速度——**假象** |
| 清缓存物理读 | 1.368 s | 1.572 s | D 稳定优于 E——**真实介质高下** |

> 这就是为什么物理读保证不可省略。

## 8. 指标定义

以分位数（p50/p90/p99）+ 均值报告延迟，以吞吐报告产能，区分首 token 与后续 token。

| 指标 | 全称 | 含义 | 单位 |
|---|---|---|---|
| TTFT | Time To First Token | 请求到第一个 token 的耗时（含 prefill / KV 加载 / 排队） | 秒 |
| TPOT | Time Per Output Token | 首 token 之后平均每个输出 token 耗时（decode） | 毫秒 |
| 请求吞吐 | Requests/s | 单位时间完成请求数 | req/s |
| 输出吞吐 | Output tokens/s | 单位时间生成输出 token 数 | tok/s |
| 总耗时 | Wall time | 完成全部请求墙钟时间 | 秒 |

**为什么 TTFT 是主角**：KV 回读发生在 prefill 阶段，命中缓存可跳过对历史前缀的重算、直接加载已算好的 KV，故存储价值主要体现在 TTFT。重算时 TTFT = 对整段长前缀重新 prefill（随长度线性增长，极昂贵）。

**分位与尾延迟**：p50（典型体验）、p90（常用 SLO 锚点）、p99（尾延迟，反映高并发最差体验）、均值（易被尾部拉高，须与分位并看）。物理读 + 高并发时，多路并发同时加载会 I/O 竞争排队，p99 显著高于 p50，这是真实代价，必须如实报告。

**指标计算口径**：
- TTFT = 流式响应中第一个含 `content` 的 chunk 到达时间 − 请求发出时间。
- TPOT = (总耗时 − TTFT) ÷ (输出 token 数 − 1)。
- 分位基于完成请求的排序数组取分位点。

**SLO 与并发拐点**：定义服务等级目标（如 p90 TTFT ≤ 2s），扫描并发找满足 SLO 的最大并发/QPS。页缓存口径的并发上限偏乐观；物理读口径才反映存储真实能力。两者都可报告，但必须标注口径。

## 9. 标准执行流程（SOP）

> 执行约定：`[宿主]` = 服务器宿主机(root)执行；`[容器]` = 推理容器内执行。`mdadm / mount / drop_caches / iostat / docker` 都是宿主命令。**populate 一律前台阻塞执行**，灌完才能进行 drop_caches / iostat / measure。各步骤的具体命令与脚本见对应厂商的复现代码页。

**阶段 0：一次性环境准备** —— 安装监控依赖（iostat）、建远端存储 RAID0 并挂载、创建推理容器、下载模型、写入测试脚本。

**阶段 1：每组测试前清场** —— 杀残留进程 + 重启容器彻底释放显存（规避引擎子进程残留），清空磁盘层目录，定义就绪轮询。

**阶段 2：执行四档** —— 每档动作序列：

```
起服务（指定磁盘层）→ 等待就绪
  → populate（前台，灌满）
  → [仅②②′] du 校验落盘 + 清页缓存 + iostat 后台
  → measure（前台，出指标）
  → 取证（need-to-load 计数 + iostat 峰值 + 结果 JSON）
```

**阶段 3：取证与归档**

| 取证项 | 期望 |
|---|---|
| 物理读命中数（measure 段 need-to-load 非 0 行数） | ②②′ = N_meas；③ = 0 |
| GPU 命中数（need to load: 0 行数） | ② = 0 |
| 物理读带宽（iostat 设备 rkB/s 峰值） | GB/s 量级 |
| 落盘量（磁盘层目录 du） | 与会话数×单会话KV吻合 |

归档：结果 JSON、服务日志（含 need-to-load 原文）、iostat 日志、编排日志。

## 10. 有效性校验清单

每份结果发布前逐条核对；任一 C/D 项不满足，该数据不得标注为"物理盘命中"。

**A. 单一变量**
- 对照各档仅一个变量不同。
- 每次起服后已校验环境变量（磁盘层指向、CPU 层、显存利用率一致）。
- 配置切换之间已重启容器彻底释放显存。

**B. 容量与溢出**
- 已实测登记 GPU KV 容量与可容纳会话数。
- 超容量档 M 确实大于 GPU+CPU 容量。
- GPU 命中档 M 小于 GPU 容量且验证 need-to-load=0。

**C. 物理读保证（核心）**
- populate 会话数 ＞ measure 会话数，measure 只读被驱逐的低编号段。
- measure 前已清页缓存并验证 buff/cache 显著下降。
- measure 每会话只读一次。

**D. 三重取证**
- need-to-load ＞ 0 计数 = measure 请求数（②②′）。
- computed tokens = 0（无 GPU 命中）。
- iostat 实测物理读 GB/s 量级，与 retrieve 吞吐互证。
- 落盘量与"会话数×单会话KV"吻合。

**E. 指标完整性**
- 报告 TTFT 的 p50/p90/p99/均值（不只 p50）。
- 报告 TPOT、请求吞吐、输出吞吐、总耗时。
- 高并发尾延迟如实呈现。

**F. 诚实披露**
- 未强制物理读（页缓存辅助）的数据已明确标注。
- "装得进显存"与"超容量"分别报告。
- 负载性质（合成/真实）已说明，并附 SUT 与完整命令。

## 11. 陷阱与踩坑

| # | 现象 | 根因 | 修正 |
|---|---|---|---|
| 1 | 测出"存储很快"但 iostat 物理读≈0 | 大内存把 KV 页缓存在 RAM | measure 前清页缓存 + iostat 验证 |
| 2 | 物理读出现 0.085s 超快点 | measure 读了仍在 GPU APC 的会话 | populate ＞ measure，只读低编号段，不复用 |
| 3 | 切配置后新服务起不来、显存被占 | pkill 杀不掉引擎子进程，驱动不回收 | 每次切换用重启容器 |
| 4 | 单段共享前缀压测测不到存储 | 前缀被去重稳留 GPU、不溢出 | 多会话互异前缀 + 超容量 M + 清页缓存 |
| 5 | measure 测到半空缓存 / 清缓存抢跑 | populate 后台启动 | populate 前台阻塞执行 |
| 6 | 宿主脚本日志不生成 | 宿主脚本写到容器内才有的路径 | 宿主脚本日志写宿主路径 |
| 7 | 后台任务被回收 | SSH 通道关闭回收进程组 | 用 `setsid ... < /dev/null &` |
| 8 | 异步/逐层预取崩溃 | LMCache 旧版本并发缺陷 | 用同步路径或升级 LMCache |
| 9 | 非 NVIDIA 平台 GDS 不可用 | GDS 后端硬依赖 NVIDIA cufile | 走常规路径，待软件适配 |

## 12. 术语表

| 术语 | 含义 |
|---|---|
| KV Cache | Transformer 推理缓存的注意力键值，避免重复计算历史 token |
| TTFT / TPOT | 首 token 耗时 / 后续每 token 耗时 |
| Prefill / Decode | 推理首阶段（处理前缀生成首 token，可被 KV 命中加速）/ 续阶段（逐 token 生成） |
| APC / prefix caching | 自动前缀缓存，复用共享前缀 KV（驻留 GPU 显存） |
| LMCache | KV 多级缓存库：GPU→CPU→磁盘分层卸载/回读 |
| need-to-load | LMCache 日志字段：本请求需从缓存层加载的 token 数；＞0 即命中缓存层 |
| NVMe-oF / RoCEv2 / RDMA | 网络化 NVMe / 以太网 RDMA / 远程直接内存访问（零拷贝、CPU 旁路） |
| page cache / drop_caches | OS 页缓存 / 清空页缓存命令 |
| iostat / fio | 设备 I/O 统计 / 标准存储基准工具 |
| GDS | GPUDirect Storage，存储直达 GPU 绕过 CPU/RAM |
| SUT / SLO | 被测系统 / 服务等级目标 |
| populate / measure | 本规范两阶段：灌入缓存 / 受控测量 |
| 绝对内存墙 | 工作集大于整机物理内存、任何 RAM 都装不下的场景 |
